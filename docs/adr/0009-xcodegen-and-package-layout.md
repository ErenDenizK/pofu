# 0009. XcodeGen project and a single local package

- **Status:** Accepted
- **Date:** 2026-10-31

## Context

[ADR-0003](0003-modular-architecture-and-screen-time-boundary.md) splits the
code into an app target plus modules (`PofuCore`, `PofuScreenTime`,
`PofuDesignSystem`, later `PofuPersistence`, `PofuCompanion`, and app
extensions). Two questions follow: how the Xcode project is maintained, and
how the modules are packaged.

Forces at play:

- **Most code is written by an agent on Linux, without Xcode.** Whatever
  defines the project must be plain text that can be written and reviewed
  without opening Xcode, and validated on CI.
- **`project.pbxproj` is hostile to review and merging.** It is a
  machine-generated graph of opaque identifiers; every added file touches
  several sections, and concurrent branches conflict constantly.
- **Extensions are coming** (shield configuration, shield action, device
  activity monitor, report, widgets). Each adds a target with its own
  entitlements and build settings, multiplying pbxproj churn.
- **The founder builds on a Mac** with Xcode 26 and must be able to get from
  a fresh clone to running on device in minutes.

## Options considered

### Project definition

1. **Hand-maintained `.xcodeproj`.** Zero tooling, the Xcode default. Every
   change happens in the Xcode UI; the agent cannot reliably author it from
   Linux; reviews of pbxproj diffs are meaningless; merge conflicts are
   frequent.
2. **XcodeGen.** A small YAML spec (`project.yml`) generates the project.
   Readable diffs, no pbxproj conflicts (the project is not committed), and
   simple to author. A single-purpose, mature, widely used tool with no
   runtime footprint in the app. Adds one `brew install` and one command
   after each pull.
3. **Tuist.** Swift-based manifests, caching, module graph tooling. More
   powerful, but a larger tool with its own versioning, a workspace
   abstraction, and features (binary caching, cloud) we do not need at our
   size. Its manifests require a Swift toolchain to evaluate, which the
   agent environment lacks.
4. **Pure Swift Package with an app target** (Xcode's package-based
   projects). Not yet able to express app extensions, entitlements, and
   signing the way we need.

### Packaging the modules

1. **One local package per module.** Strongest isolation, but each module
   repeats platform declarations, language settings, and tooling, and
   Xcode shows several package nodes.
2. **One local package with several targets.** Module boundaries are still
   enforced by the compiler (a target can only import what it declares),
   while settings, platforms, and tests live in one manifest.

## Decision

- The Xcode project is **generated by XcodeGen** from `project.yml` at the
  repository root. `*.xcodeproj` is ignored by git. Build settings live in
  the spec; the Info.plist is generated from `INFOPLIST_KEY_*` settings.
- All non-app code lives in **one local package, `Packages/PofuKit`**, with
  one library target per module and one test target per testable module.
- `PofuCore` has zero dependencies and imports Foundation only, so it
  builds and tests anywhere Swift runs, including Linux.
- The package declares macOS as a platform only so that `swift test` runs on
  any Mac and CI runner without a simulator; the product ships on iOS.
- The bundle identifier and signing team live in `Config/Pofu.xcconfig`,
  with `DEVELOPMENT_TEAM` empty. It optionally includes a git-ignored
  `Config/Local.xcconfig` where each developer sets their team (and, on a
  free Personal Team, a development bundle identifier). CI builds unsigned.

## Consequences

- The agent can add files, targets, and settings from Linux; reviewers read
  YAML and Swift, never pbxproj.
- After cloning or pulling, developers run `xcodegen generate` (documented
  in [development.md](../development.md)). Forgetting it shows up quickly
  as missing files in Xcode.
- Signing settings changed in the Xcode UI are lost on the next
  generation; `Config/Local.xcconfig` is the durable place for them.
- If we outgrow XcodeGen (many extensions, build caching needs), migrating
  to Tuist is mechanical: both describe the same targets and settings.
- Splitting `PofuKit` into several packages later is cheap, because modules
  already depend on each other only through declared target dependencies.
